# Goofy Ball — свой сервер Nakama

В итерации 1 сервер поднимаем **на своём компьютере**, без хостинга. Сервер ничего не считает:
он выдаёт код комнаты и seed матча и пересылает ввод игроков между ними (relay).
Игру считает каждый клиент сам (детерминированная симуляция + rollback).

## Что нужно
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) (Windows: бэкенд WSL2). Проверка: `docker version`.
- Свободный порт **7350** (HTTP API + WebSocket).

## Запуск

```powershell
cd server
copy .env.example .env      # затем поменяй пароли и ключи в .env
docker compose up -d
docker compose logs -f nakama   # ждём строку "Startup done"
```

Проверка с этого же компьютера: http://127.0.0.1:7350/healthcheck → `{}`.
Консоль администратора — только с этого компьютера: http://127.0.0.1:7351/ (логин и пароль из `.env`).

Остановить: `docker compose down`. Стереть базу целиком: `docker compose down -v`.

## Как подключаются игроки

| Кто | Адрес сервера в игре («С другом» → «Сервер:») |
|---|---|
| Игра на этом же компьютере | `127.0.0.1:7350` (по умолчанию) |
| Другое устройство в той же Wi‑Fi сети | локальный IP компьютера: `ipconfig` → IPv4, например `192.168.1.10:7350` |
| Друг через интернет, у тебя белый IP | проброс порта **7350/TCP** на роутере → твой внешний IP, например `85.1.2.3:7350` |
| Друг через интернет, белого IP нет | [Tailscale](https://tailscale.com/) или [ZeroTier](https://www.zerotier.com/) у обоих → IP компьютера в этой сети, например `100.64.0.5:7350` |

Адрес сохраняется на устройстве (`user://online.cfg`), пересобирать игру не нужно.

**Чтобы не вписывать адрес на каждом устройстве:** скопируй `online_local.cfg.example` в `online_local.cfg` в корне проекта и впиши IP своего компьютера с сервером. Файл не попадает в git, но попадает в твои сборки (Windows, Android) и в запуск из редактора — новые установки сразу знают твой сервер. Поле «Сервер» в игре по-прежнему сильнее: если на устройстве раньше сохраняли другой адрес, впиши нужный ещё раз (или сотри данные приложения).
Windows спросит разрешение брандмауэра для Docker при первом входящем подключении — разреши для частной сети.

## Безопасность
- Наружу открыт только 7350. Postgres доступен только контейнеру Nakama, консоль 7351 — только с этого компьютера.
- Перед тем как открывать порт в интернет, поменяй в `.env` всё: `POSTGRES_PASSWORD`, `NAKAMA_CONSOLE_PASSWORD`,
  `NAKAMA_SESSION_KEY`, `NAKAMA_REFRESH_KEY`, `NAKAMA_CONSOLE_SIGNING_KEY`, `NAKAMA_HTTP_KEY`, `NAKAMA_SERVER_KEY`.
- Если меняешь `NAKAMA_SERVER_KEY`, тот же ключ нужен в игре: `server_key` в `src/features/online/online_config.tres`
  (пересборка) или строка `server_key=...` в секции `[nakama]` файла `user://online.cfg` на каждом устройстве.

## Честная проверка задержки
Ping в игре — это путь «игрок A → сервер → игрок B». Если сервер стоит у одного из игроков, путь почти как
напрямую и короче, чем будет через хостинг. Для честной проверки ставь сервер на третий компьютер в другом месте
или включи в игре эмуляцию сети (F3 → «Wi‑Fi», «4G», «Плохая сеть»).

## Что внутри
| Файл | Что |
|---|---|
| `docker-compose.yml` | Postgres + Nakama 3.37 |
| `nakama/local.yml` | Настройки Nakama (секреты приходят из `.env`) |
| `nakama/modules/rooms.lua` | RPC `room_create`, `room_join`, `room_close`: код из 4 символов → relayed-матч `gb_room_<КОД>` + seed матча |

Первый вошедший в матч становится хозяином (peer 1), второй — гостем. Третьего игрока клиент хозяина не пускает.
