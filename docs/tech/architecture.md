# Goofy Ball — техническая архитектура

> Геймдизайн — [`../design/GDD.md`](../design/GDD.md). Итерации — [`../roadmap.md`](../roadmap.md).

## 1. Стек
- **Клиент:** Godot 4.7, 2D, рендерер **Compatibility** (нужен для веба и слабых мобильных), GDScript.
- **Бэкенд:** Nakama + Postgres (Docker Compose локально, Heroic Cloud или VPS в продакшне).
- **Сетевой матч:** детерминированная симуляция + rollback (`godot-rollback-netcode`), Nakama работает как relay.

## 2. Структура проекта и подходы (как в `GGamezebo/quizmatik`)
Технические подходы берём из quizmatik (`.cursor/rules` там) и адаптируем под онлайн-симуляцию.

| Путь | Роль |
|---|---|
| `main.tscn` → `src/game/main.gd` | Запуск HFSM приложения |
| `src/game/hfsm/app_hfsm.json` | Фазы приложения: `App` → `Menu` / `Battle` / `PostBattle`; параллельно `Platform` (`WEB` / `Android` / `Desktop`) и `Online` |
| `src/game/scenes/{app_root,online,menu,game,post_battle}` | Экраны и контексты — только оркестрация (`IScene`: `initialize` / `deinit` / `on_event`). `online` держит соединение с Nakama, пока игрок в комнате |
| `src/features/{name}/` | Изолированные фичи: `volley_sim` (+`buffs/`), `match_session` (сессии, настройки rollback, эмуляция сети), `blob_view`, `ball_view`, `court_view`, `buff_fx`, `online` (клиент Nakama, комнаты), `net_overlay`, `virtual_controls`, `ai_opponent` |
| `src/common/` | Общие ресурсы: пресеты физики, арены, правила, персонажи, `MatchSetup` |
| `src/ui/` | Общие виджеты (кнопки, диалоги, загрузка) |
| `src/game/account/` | Прогресс, статистика, сохранения |
| `core/lib/` | Библиотеки без зависимостей от игры: `hfsm`, `event_listener`, `ResourceUtils`, `window_stack_manager`, `log` (из quizmatik; `fsm`, `shackers` — когда понадобятся) |
| `addons/` | `hfsm_editor`, `GodotSavesAddon`, Nakama, `godot-rollback-netcode` |
| `server/`, `tests/`, `tools/`, `concept/` | Сервер, headless-тесты, генераторы, арты |

**Принципы из quizmatik:**
- **Изоляция фич:** всё нужное фиче лежит в её папке, наружу выходят только сигналы `ev_*` и `initialize`/`setup`. Фичи не лезут во внутренности друг друга, сцены их компонуют.
- **Каждая сцена запускается отдельно (F6):** значения по умолчанию лежат в `.tres`. Родитель подменяет их при запуске: событие → `initialize(data)` → `ResourceUtils.update_resource`.
- **События — ресурсы `RootEvents` / `GameEvents`, а не автолоады.** Подписки через `EventListener`, отписка в `deinit`. Единственное исключение — автолоад `SyncManager` у rollback-аддона.
- **UI собирается в редакторе**, повторяющиеся элементы — шаблоны `.tscn`. Окна меню идут через `WindowStackManager`, диалоги — поверх него.
- **`class_name` и `@export` вместо жёстких путей `res://`.**
- **Mobile + Steam + HTML5 с первого дня:** тач и клавиатура/геймпад. Платформенный код живёт только в платформенных контекстах HFSM (`App/Platform` → `WEB` / `Android` / `Desktop` → магазины). Родитель один раз проверяет `OS.has_feature` и поднимает только ветку текущей платформы, игра общается с ней через события-ресурсы.
- **Слои:** `src/game` (HFSM, контексты, сцены-оркестраторы) → `src/features` (изолированные фичи) → `src/ui`, `src/common` (общие виджеты и ресурсы игры) → `core` (код без зависимостей от проекта). Зависимости идут только вниз.
- **Крупные контексты — отдельные состояния HFSM со своими сценами:** фазы приложения, платформы, онбординг, фичи, которые включает сервер. У каждого состояния есть ресурс данных по умолчанию (`.tres`, подменяется при активации состояния) и ресурс событий, через который оно общается с другими состояниями.
- **Ни одного синглтона:** ни автолоадов, ни глобального статического состояния. Исключение — сторонние плагины.
- **Переиспользование:** код, не зависящий от проекта (паттерны, утилиты, как `hfsm`), — в `core/`. Переиспользуемый, но зависящий от игры код — компоненты в `src/`. Фичи — исключение: все зависимости держат внутри себя.
- **Компоненты:** крупные объекты делим на компоненты по смыслу. Родитель создаёт детей и вызывает их методы, дети только испускают сигналы `ev_*`, подписывается на них родитель. Ссылок на родителя у компонентов нет. SOLID, без оверинжиниринга.
- **Логи:** на все крупные события (переходы HFSM, старт и конец матча, очки, бафы, сеть, сохранения, ошибки) пишем однострочные логи с уровнем `DEBUG` / `INFO` / `WARN` / `ERROR`. Уровень настраивается по каналам, лишнее отключается. Главная цель — чтобы AI-агенты находили баги по логу. Логгер — в `core/lib/log/`, без синглтона.
- **Сохранения:** `SaveManager` через `RootEvents.ev_save_progress`, с задержкой и не во время боя.

**Отличие от quizmatik:** правила матча (подача, розыгрыш, очко, конец) живут **внутри детерминированной симуляции**, а не в отдельной FSM `GameManager`. Иначе rollback не сможет их откатывать. Сцена `game` только собирает симуляцию, сессию, отображение и HUD.

## 2.1 Главный принцип
**Клиент отправляет только ввод. Игру считает одна чистая детерминированная симуляция.**
Все режимы (против AI, вдвоём на одном ПК, онлайн) и будущий авторитарный сервер используют один и тот же код игры. Различается только то, откуда приходит ввод и где запущена главная копия симуляции.

```
MatchSetup (данные) ──► Sim.reset(setup, seed)
ввод[игроки] ──► Sim.step(inputs) ──► SimState ──► View (2D, слайм, glow, камера)
                    │
                    ├ Physics: params = preset ⊕ стек модификаторов
                    ├ Rules:   TwoTeamPoints | MultiZoneLives
                    ├ Buffs:   реестр (passive / pickup / env)
                    └ EnvDirector: колода событий из seed
MatchSession: Local | Rollback(relay) | Authoritative(позже)
```

## 3. Данные матча (ресурсы `.tres`, без кода)
- `PhysicsPreset`: гравитация, прыжок, скорость, трение, упругость и затухание мяча, макс. скорость, радиусы.
- `ArenaPreset`: размер (S, M, L), высота сетки, потолок, точки появления пикапов, число зон.
- `CharacterDef`: id, пассивный баф, косметика по умолчанию.
- `RuleSet`: `points` или `lives`, лимиты, касаний на команду, взрыв разрешён или нет, частота событий, колоды событий и пикапов с весами.
- `MatchSetup`: `teams: [{id, slots: [{player_id, character_id, is_bot, peer_id}]}]` + пресеты + `seed`. Один формат для всех режимов и тестов.

## 4. Состояние симуляции
`SimState` — обычный Dictionary или массивы с примитивами, чтобы его можно было сохранить, загрузить и посчитать хеш:
`players[]`, `balls[]`, `zones[]`, `nets[]`, `pickups[]`, `hazards[]`, `modifiers[]`, `rng`, `score`/`lives` по командам, `phase`, `tick`, `view` (наклон и переворот камеры), `*_serial` (счётчики для визуальных эффектов).

- Нет понятий «левый» и «правый»: только индексы игроков и команд. Поддерживаются N игроков в команде и N команд.
- Мячей сразу несколько (`balls[]`), на случай события «мультимяч».
- `ball.last_toucher` (игрок и команда): по нему определяется, кто получает пикап при попадании мячом.

## 5. Система эффектов
- **`Modifier`**: `{def_id, target: GLOBAL|TEAM|PLAYER|BALL, params, ticks_left (-1 = навсегда), source}`.
- **Физика** всегда читает параметры через `param(name, target)`: значение пресета, к которому применён стек модификаторов (умножение, сложение, переопределение).
- **`BuffBase`**: `kind` (PASSIVE, PICKUP, ENV) и хуки `on_grant`, `on_activate`, `on_tick`, `on_contact`, `on_expire`. Хуки работают только через API симуляции: `add_modifier`, `spawn_hazard`, `apply_impulse`, `explode`, `rng`.
- **`BuffRegistry`**: id → определение. **Новый баф = файл логики + файл визуала + `TrialDef` испытания-знакомства**, ядро не трогается.
- **`TrialDef`** (`.tres`, без кода): `MatchSetup` (арена, пресет, бот со скриптом, баф в слоте), цель — предикат над `SimState` («гол после портала», «3 отскока»), пороги трёх звёзд (счётчик, время), подсказки поверх экрана, глава. Испытание идёт через ту же детерминированную симуляцию, поэтому проверяется теми же headless-тестами: на каждый `TrialDef` — эталонный лог ввода, который берёт ★.
- **`self_destruct`** — тоже баф: срабатывает по кнопке, когда слот пуст.
- **`EnvDirector`** тянет события из колоды по `rng`, с предупреждением за 1–2 с.
- **Камера** (наклон, переворот, тряска) — это значения в `SimState.view`. `View` их только отображает, на физику они не влияют.

## 6. Детерминизм (обязателен)
- В симуляции только `+ - * /` и `sqrt` над float. **Никаких `sin`/`cos`/`atan2`**: углы берём из своей таблицы или храним как готовые векторы.
- Нет физики Godot, нод, `randf()`, wall-clock: время только в тиках (60 Гц).
- Случайность только из `rng` в состоянии (xorshift на int), seed выдаёт сервер.
- Фиксированный порядок обхода, никаких итераций по Dictionary с неопределённым порядком.
- Визуальные эффекты выводятся из `*_serial` в состоянии, а не вызываются из `step()`, иначе откат их продублирует.
- Слайм-деформация и конечности только во `View`. Если у конечности есть геймплейное действие, это отдельный простой хитбокс в симуляции.
- **Кросс-платформенный детерминизм** (Windows x86 ↔ Android ARM) проверяется в итерации 1: один лог ввода → один хеш. Не совпал — симуляция переходит на фиксированную точку (int). В состоянии симуляции — скалярные `float`, без `Vector2`.

## 7. Отображение
- Блоб: кольцо из 16–24 точек на пружинах, гладкий контур, блик, обводка.
- Glow: `WorldEnvironment` + 2D HDR. **Проверить работу в Compatibility на Godot 4.7.** Если не работает, используем additive-ореолы спрайтами.
- Визуал каждого бафа лежит в `src/features/buff_fx/<buff_id>/`, логика — в `src/features/volley_sim/buffs/<buff_id>.gd`.

## 8. Сеть
### Сессии
- `LocalSession`: против AI и вдвоём на одном ПК (кнопку «Вдвоём» показывает только `DesktopContext` через `PlatformCaps`).
- `RollbackSession`: `SyncManager` поверх Nakama relay. Поддерживает несколько peer-ов, ориентир — до 8 игроков. Один узел `RollbackInput` на слот, authority = `peer_id` слота из `MatchSetup`.
- Ручки rollback — `NetTuning` (`.tres`): задержка ввода (2 тика), буфер отката (60 тиков = 1 с: задержки Wi‑Fi до секунды прячутся откатом, а не замиранием), до 10 с на восстановление синхронизации, лимиты сообщений, допуск рассинхрона. Пока синхронизация потеряна, `RollbackSession` обходит две взаимоблокировки аддона: пересчитывает последний тик каждый кадр и отправляет весь неподтверждённый ввод заново.
- `LagNetworkAdaptor` (в debug-сборках): эмуляция задержки, джиттера и потерь исходящих пакетов (`LagProfile`: Wi‑Fi, 4G, плохая сеть, Wi‑Fi со спайками, обрывы по 1,5 с). Порядок пакетов сохраняется, как в TCP relay.
- Плавность на экране — во `View`: позиции пишутся в кольцевой буфер по тикам (и переписываются при пересчёте после отката), рисуются между двумя последними тиками, а скачок после отката превращается в смещение, которое гаснет за ~0,1 с.
- Сетевой оверлей (F3 / три пальца): ping, откаты, пропуски тиков, рассинхроны, FPS, проверка детерминизма (`DeterminismProbe`).
- `AuthoritativeSession` (позже): headless-Godot на сервере запускает **ту же** симуляцию, клиент предсказывает и откатывается к серверному состоянию.

### Почему rollback + relay
- Позиции игроков по сети не передаются: каждый клиент считает их сам из одинакового ввода.
- **Relay, а не P2P на старте:** работает за любым NAT, скрывает IP, ведёт серверный лог ввода (античит, реплеи). Транспорт сменный, P2P через WebRTC можно добавить позже для комнат.
- **Матчи из общей очереди (все на рейтинг) всегда через relay.**

### Стоимость relay (оценка, уточнить нагрузочным тестом)
- Матч 2 игрока: примерно 12–24 КБ/с исходящего трафика, 2–4 МБ за 3-минутный матч.
- 1000 матчей одновременно: примерно 100–200 Мбит/с, 1–2 сервера по 4–8 vCPU.
- Оптимизации: ввод 30 Гц пачками по 2 тика, protobuf вместо JSON, relayed-матчи по умолчанию, авторитарный обработчик — только для спорных рейтинговых матчей.

### Античит в рейтинговых матчах
1. Сервер выдаёт seed, нумерует тики и пишет лог ввода.
2. Клиенты присылают результат и хеш состояния.
3. При расхождении headless-Godot прогоняет лог той же симуляцией и выносит вердикт (позже).

## 9. Бэкенд (Nakama)
- Аккаунты: тихий вход по платформе (Play Games / Game Center / Steam), в браузере — гость + мягкое сохранение (Google / Apple / код устройства). Линковка = несколько ключей на один Goofy ID; UI — `concept/ui.md`.
- Матчмейкер: одна очередь на рейтинг (Glicko-2: ставка зависит от разницы рейтингов, диапазон поиска расширяется по времени).
- Комнаты по коду.
- Лидерборды (глобальный, недельный, друзья, страны).
- Кошелёк, инвентарь, проверка покупок для косметики.

## 11. Тесты
- Детерминизм: один seed и один лог ввода, запущенные дважды, дают одинаковый хеш (со всеми бафами и событиями).
- Сохранение и загрузка состояния посреди матча дают тот же хеш.
- Общий тест для каждого `BuffDef`: выдача, активация, истечение, без утечек модификаторов.
- Матчи 1×1, 2×2 и три команды по одному игроку с ботами доходят до конца.
- Rollback с искусственной задержкой и потерей пакетов; e2e на двух процессах.
- Кросс-платформенный хеш: один лог ввода на Windows и Android.
