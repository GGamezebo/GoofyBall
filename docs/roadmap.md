# Goofy Ball — roadmap

> Детали: [`design/GDD.md`](design/GDD.md), [`tech/architecture.md`](tech/architecture.md).

## Принцип
- **Итерации — вертикальные срезы, а не слои.** Каждая заканчивается играбельной сборкой для PC и Android, которую проверяют живой игрой.
- Итерация закрыта, только когда выполнены её критерии «Готово, когда». Следующую уточняем после неё.
- Сеть проверяется с первой итерации: каждая новая механика должна работать онлайн под откатами без рассинхрона.

## Итерация 1 — Сетевой срез
**Статус:** реализовано в ветке `feature/iteration-1-network-slice`, ждёт плейтеста. Что сделано и как пользоваться — [`iteration-1.md`](iteration-1.md).

**Цель:** двое на разных устройствах и в разных сетях играют 1×1 через интернет, и игра идёт **плавно, без лагов**. Всё остальное — минимум, нужный для этой проверки.

**Входит:**
- **Каркас по образцу quizmatik:** `main.gd` + `app_hfsm.json` (`App` → `Menu` → `Battle`), `app_root` с `RootEvents`, логгер `core/lib/log/`. Рендерер Compatibility. Каждая сцена запускается по F6. Без сохранений и аккаунтов.
- **Симуляция `volley_sim`:** мяч, сетка, стены, подача, правило `TwoTeamPoints` до 7. Модель данных сразу N команд × N игроков (`MatchSetup`), но играем только 1×1. Один пресет физики Classic, одна арена S.
- **Один персонаж:** блоб без пассивки. Графика — заглушки: круги, сетка, счёт. Бафов, событий, самоуничтожения и кнопки «Действие» нет.
- **Управление:** клавиатура (P1 `A`/`D`/`W`, P2 `←`/`→`/`↑`), геймпад, на телефоне тач (левая половина — движение, справа — прыжок).
- **Режимы** (меню из нескольких кнопок):
  - **Против AI:** простой бот бежит под точку падения мяча и прыгает; одна сложность. Бот — такой же источник ввода, как игрок.
  - **Вдвоём на одном ПК:** два набора клавиш. Кнопка есть только на PC.
  - **С другом:** комната по коду. «Создать» показывает код из 4 символов, друг вводит его в «Войти по коду». Вход гостем по id устройства, без экранов аккаунта.
  - Конец матча: счёт и кнопки «Ещё раз» / «В меню».
- **Прямое соединение (добавлено по итогам плейтеста):** relay по TCP на телефонном Wi‑Fi замирал на 1–4 с, поэтому игра в комнате идёт напрямую по UDP (WebRTC P2P), Nakama — для кода комнаты, «знакомства» игроков и как запасной путь.
- **Свой сервер:** Nakama relay поднимаем на своих компьютерах (docker compose), хостинга нет. Наружу открыт только порт API `7350`: проброс на роутере, если IP белый, иначе Tailscale или ZeroTier. Консоль `7351` наружу не открываем, ключ сервера и пароль консоли меняем с дефолтных. Адрес сервера задаётся в настройках (`.tres` + файл на устройстве), без пересборки.
- **Сеть:** `RollbackSession` = `SyncManager` поверх Nakama relay, по сети идёт только ввод. Задержка ввода и глубина отката задаются в `.tres`. Сверка хеша состояния; при рассинхроне — лог с тиком и обоими хешами, матч прерывается с сообщением.
- **Плавность на экране:** после отката мяч и чужой блоб доезжают до верной позиции, а не телепортируются: мелкая поправка за ~0,1 с, большая — до ~0,3 с (сглаживание только во `View`). Если экран больше 60 Гц — интерполяция между тиками.
- **Сетевой оверлей** (F3 или касание тремя пальцами): ping, задержка ввода, откатов в секунду, макс. глубина отката, потери, рассинхроны, FPS. Итог матча с этими числами пишется в лог.
- **Эмуляция плохой сети** в отладочной сборке: задержка, джиттер, потери; пресеты «Wi‑Fi», «4G», «плохая сеть».
- **Сборки:** Windows и Android APK из CI, чтобы раздать друзьям.
- **Тесты:** детерминизм (seed + лог ввода → один хеш), сохранение и загрузка посреди матча → тот же хеш, e2e двух процессов с задержкой и потерями — в CI.

**Не входит:** хостинг сервера, бафы, события, персонажи с пассивками, аккаунты, рейтинг, очередь, друзья, 2×2, веб, арт, звук, сохранения, монетизация.

**Порядок работ** (каждый шаг можно проверить руками):
1. Каркас, логгер, симуляция, «Вдвоём на одном ПК» — играем локально, настраиваем физику Classic.
2. Сеть: свой сервер Nakama, комната по коду, rollback, оверлей, эмуляция сети, e2e в CI — играем PC ↔ PC через интернет.
3. Android: тач, APK — играем PC ↔ телефон. **Первым делом сравнить хеши одного лога ввода на Windows и Android.**
4. Бот «Против AI».
5. Плейтест: матчи с друзьями в разных сетях (Wi‑Fi ↔ 4G), сбор логов, подбор задержки ввода и глубины отката.

**Готово, когда:**
- 10 матчей до 7 подряд между разными сетями (PC ↔ PC, PC ↔ Android, Wi‑Fi ↔ 4G) — без рассинхронов и разрывов.
- При ping до 120 мс игроки не замечают телепортов мяча и рывков соперника; свой блоб откликается сразу (задержка ввода не больше 2 тиков, ~33 мс).
- При эмуляции 200 мс + джиттер 30 мс + 5 % потерь игра остаётся играбельной и не рассинхронизируется.
- Стабильные 60 FPS на среднем Android-телефоне, в том числе при откатах.
- Тесты и e2e зелёные в CI. По логу одного матча видно ping, откаты и причину любого разрыва.
- Большинство участников плейтеста отвечают «не лагает».

**Риски:**
- **Детерминизм float между x86 (Windows) и ARM (Android).** Проверяется на шаге 3. В симуляции — скалярные `float` (64 бит), без `Vector2` (32 бит, считается в C++). Если хеши разошлись — переводим симуляцию на фиксированную точку (int).
- **Ping через relay** = путь A → сервер → B; ping в оверлее и логе показывает именно этот путь. Если сервер стоит у одного из игроков, путь почти как напрямую и короче, чем будет через хостинг. Чтобы проверка была честной, сервер ставим на третий компьютер в другом месте или добавляем эмуляцией +50 мс.
- Код из старых веток (Godot 4.7, `SyncManager` + мост Nakama) может не завестись сразу.

**Берём из старых веток** (приводим к правилам: N команд, логгер, без новых синглтонов):
- `claude/mobile-game-build-run-le59yg`: `volley_sim.gd`, `online_rollback.gd`, `rollback_input.gd`, `ai_opponent.gd`, `virtual_controls`, `tests/` и e2e `online_peer.gd`, CI Android APK, `server/` (комнаты).
- `prototype-3d`: аддоны Nakama и `godot-rollback-netcode`.
- quizmatik: `core/lib` (`hfsm`, `fsm`, `event_listener`, `ResourceUtils`), `addons/hfsm_editor`.
